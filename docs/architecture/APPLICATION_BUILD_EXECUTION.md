# Isolated application build execution

Prompt 32A adds the provider-neutral execution boundary that consumes one
immutable Solution Revision and a separately produced workload source tree. It
is implemented by `@cloudmarkup/application-build-runner`; it is not part of the
application generator, solution exporter, Go compiler, or Terraform renderer.

The reviewed generated runtime profile accepts two exact generator families: the
Prompt 29A notes descriptor and the Prompt 45A curated-event descriptor. Both
retain the same runtime and fixed execution surface:

- Lambda `nodejs24.x` with Node.js `24.18.0`;
- TypeScript `6.0.3`, ESM, archive entry `index.js`, handler `index.handler`;
- pnpm `11.16.0` with a version-9 frozen lockfile;
- Vitest `4.1.10`; and
- the exact admitted generator/template/pattern/dispatcher, runtime,
  build-envelope, dependency, source, and artifact-path commitments.

Adding another language, runtime, package manager, command, lifecycle-script
exception, dependency set, scanner, or image requires another reviewed profile.

## Boundary and interfaces

The version-1 request contains:

- the exact Solution Revision manifest and its canonical digest;
- either an admitted Application Generation Result plus one exact workload
  build-contract digest, or explicitly user-provided source;
- the exact runtime/profile selection;
- an integrity-bearing dependency contract containing frozen lock bytes,
  package-manager pin, package-manifest checksum, sorted package inventory,
  registry integrity values, tarball digests, and offline-cache digest;
- CPU, memory, process, wall-time, output, file-count, file-size,
  total-workspace, and artifact-size limits; and
- an optional cancellation signal supplied to the runner, outside the serialized
  request.

The result contains deterministic state, bounded sanitized diagnostics, fixed-
command summaries, unit and contract test summaries, dependency/secret findings,
content-addressed artifacts, a CycloneDX dependency manifest, coverage
confirmation or downgrade, Evidence v1, and a canonical report digest. Public
schema refinement independently verifies canonical base64, artifact
sizes/checksums, Evidence artifact commitments, passing/non-passing invariants,
and the outer report digest.

One runner request still builds exactly one workload. The immutable Solution
export workflow may supply either that singular compatibility form or the
bounded canonical batch defined by
[ADR-0037](../adr/0037-deterministic-multi-artifact-application-build-batches.md).
The batch must cover every eligible generated build contract exactly once and is
ordered by workload/build-contract identity. The aggregate stage invokes the
same Prompt 32A runner once per entry, preserves one Evidence record and
artifact set per workload, and passes only when every invocation passes.
Missing, extra, duplicate, colliding, malformed, or failed entries block the
final export; successful partial output is never downloadable.

The runner receives an injected workspace executor so local containers, later
workers, and fake test executors share the same data-only interface. Source
cannot choose an executable, argument, package script, scanner configuration,
network policy, output path, or Evidence claim.

## Admission and fixed execution

Generated execution is admitted only when all of these conditions hold:

1. the Solution Revision, exact notes or curated-event generator artifact,
   source manifest, and build envelope bind the same immutable revision and
   approved descriptor;
2. generator, runtime, handler, toolchain, package manifest, dependency set,
   lock bytes, package-manager binary, offline store, and requested profile
   equal their approved pins;
3. the generation result has no producer error or ownership/materialization
   conflict and its mode is `generated-starter` or `complete-supported-pattern`;
4. every build input has its exact generated bytes, checksum, safe path, and
   allowed content type;
5. the source tree contains no secret-shaped value, local-machine path, cache,
   dependency tree, state/plan file, symlink, device file, case/NFC collision,
   or limit violation; and
6. the package manifest has no scripts and the lock uses lifecycle policy
   `deny`, a prepackaged content-addressed cache, and network policy `deny`.

The runner then selects fixed executable-plus-argument arrays, never a shell
string:

1. exact offline, frozen, hook/workspace/pnpmfile-disabled `pnpm install`
   against the prepackaged store, using a hoisted copy linker with bin links and
   symlinks disabled;
2. generated-code ESLint with a fixed image-owned configuration;
3. TypeScript type checking;
4. Vitest unit tests selected by the fixed `unit.test.ts` path filter;
5. Vitest contract tests selected by the fixed `contracts.test.ts` filter;
6. offline Trivy dependency scanning;
7. offline Trivy secret scanning;
8. TypeScript compilation without declarations or source maps; and
9. explicit hook-free, frozen offline `pnpm install --prod` reconciliation.

After pruning, the adapter admits only the exact physical runtime and
transitive-runtime inventory bound by the structured lock contract. Residual
development packages, executable `.bin` entries, a populated virtual store,
unknown identities, symlinks/devices, or an incomplete runtime inventory fail
closed. The root-only regular `.package-map.json`,
`.pnpm-workspace-state-v1.json`, `.modules.yaml` and a `.pnpm` directory
containing only one regular `lock.yaml` are inert package-manager metadata and
are excluded from the ZIP. Unknown hidden metadata remains an error.

Successful test and scanner exit codes are not trusted alone. Test output must
be bounded JSON with at least one passing test, and scanner output must be
bounded Trivy JSON. A malformed result, timeout, cancellation, excessive output,
unavailable tool, high/critical vulnerability, or secret finding stops the
sequence and prevents packaging.

User-provided source is disabled by the generated profile. The explicit
`user-provided-static-only` profile may perform the frozen install, lint, type
check, and offline scans, but it never runs tests or source, never packages an
artifact, and always leaves complete coverage downgraded. No arbitrary unknown
package script is executed under either profile.

## Local container adapter

The initial local adapter accepts only an absolute Docker or Podman executable
selected by trusted configuration. Each command starts the exact image by digest
with:

- `--network none`, `--pull never`, read-only root, no capabilities,
  `no-new-privileges`, and non-root UID/GID;
- no privileged mode, host socket, device, credential, AWS environment, customer
  role, or deployment permission;
- exact CPU, memory, PID, timeout, bounded tmpfs, output, file-count, file-size,
  and total-workspace limits;
- a newly created, validated workspace mounted only at `/workspace`; and
- a scrubbed fixed environment.

The adapter validates the workspace after every command, reads only regular
files under the approved compile/dependency output roots, and removes the exact
temporary workspace even when a command fails. The service never returns its
absolute path.

## Deterministic Lambda package

Only conflict-free generated builds can produce a package. Packaging maps every
generated runtime TypeScript input, including the curated-event generated no-op
runtime seam, to its exact compiled JavaScript path. It requires every direct
runtime dependency's package metadata and excludes tests, source maps,
TypeScript source, caches, local environment files, credentials, and user-owned
extension output. `extensions/custom.ts` remains reviewable source but is never
a generated-profile ZIP entry; activating it requires a separately reviewed
custom-source build profile.

The ZIP writer accepts only unique portable regular paths, sorts in UTF-16
order, stores bytes without compression, fixes the DOS timestamp to the ZIP
epoch, uses regular `0644` metadata, emits no comments or extras, and verifies a
second reverse-input assembly is byte-identical. The returned ZIP path is the
unchanged Prompt 29 contract:

`application/artifacts/<portable-workload-segment>/function.zip`

The builder also returns a canonical CycloneDX 1.6 SBOM. Each file records its
bytes, media type, size, SHA-256 checksum, generated-build ownership, build-
contract digest, dependency-lock digest, revision digest, source checksums, and
workload ID. Terraform semantics remain graph-derived; the build never scans
source to add IAM or change infrastructure.

Every passing build also returns
`application/artifacts/<portable-workload-segment>/artifact-manifest.json`. That
canonical target-neutral record binds the final ZIP path/media type/SHA-256,
runtime, handler, compiled entrypoint, workload, build contract, generation
artifact, and Solution Revision. Terraform and CloudFormation consume the same
final ZIP contract; this build boundary does not select or render either IaC
target.

## Evidence and coverage

A passing generated build creates level-5 application-build-and-tests Evidence
whose checks separately cover build/tests/reproducibility and application
security. It binds exact input and artifact digests plus the builder, container,
toolchain, and scanner pins. The result may confirm the generator's input
coverage state only when every required command, generated unit/contract test,
scan, package check, and reproducibility check passes.

Failure, error, cancellation, admission block, cleanup failure, or static-only
user validation returns no deployable artifact or coverage Evidence binding and
downgrades the confirmed state to `custom-implementation-required`. This is a
new assessment; the immutable Solution Revision is never mutated.

Prompt 31 remains a pure exporter. Its application-build adapter accepts only
schema- and digest-verified passing singular or canonical-batch results,
preserves ZIP/manifest/SBOM ownership as `generated-build-artifact`, writes each
Evidence record as `evidence-artifact`, rejects cross-workload path or identity
collisions, and returns supplemental data to the export service. It never
invokes the builder.

## AWS validation sandbox

The Application CDK stack now also defines an inert application-build CodeBuild
project separate from Terraform validation. It has its own role, log group,
security groups, S3 input/output/Evidence prefixes, digest-pinned image,
non-privileged medium compute, no source, no cache, no trigger, no caller grant,
fixed service command, explicit timeout/queue/concurrency/resource values, and a
monthly build-minute configuration hook.

IAM can read only the application-build input prefix, write only its artifact
and Evidence prefixes, write its bounded log group, pull the one approved ECR
repository, and create its isolated network interfaces. The project has no
secret, STS role-assumption, CloudFormation, Lambda update, Terraform plan/
apply, or customer-account permission. Its VPC security group has no public
egress and can reach only dedicated S3 and CloudWatch Logs endpoints. Storage
and logs use the platform's encrypted, lifecycle-managed boundaries.

The repository synthesizes this definition only. The configured development
image digest is a deterministic synthesis coordinate, not proof that an image
was built, signed, published, or executed, and no CodeBuild project is deployed
by this prompt.

## Verification and limitations

Unit tests use fake workspace executors to cover success, lint/type/test/scan
failures, tampered dependencies/locks/results, lifecycle scripts, secrets,
unsafe paths, limits, cancellation, reproducible ZIPs, excluded files, ownership
profiles, coverage, and Terraform artifact compatibility. Separate reviewed
integration harnesses materialize only the exact generated complete notes tree
and the exact two-workload curated-event fixture. They use pinned repository
Node, TypeScript, and Vitest tools plus reviewed local stubs to type-check,
execute generated unit/contract tests, and compile without network or
credentials. They validate generated code but do not create production Evidence
or substitute for the pinned container.

A separate local-adapter regression drives the real runner and disposable
workspace/session through a test-only process seam. It asserts the complete
shell-free container argument vector, the ordered nine-step command evidence,
the regular physical production closure, byte-identical ZIPs, and fail-closed
link/prune cases without starting Docker or using a network. That regression
validates the structured lock inventory against physical output; it does not
cryptographically derive the complete pnpm v9 graph from YAML.

The repository does not build or publish the configured container image or
offline dependency store, execute Docker/Podman in ordinary checks, contact a
package registry during a build, upload artifacts, invoke CodeBuild, or deploy.
Those operational steps require separately reviewed image/store provenance,
worker authorization, tenant isolation, persistence, and release policy.

## Prompt 36A AI-assisted build profile

The additive `cloudmarkup.application-build.ai-assisted-custom-nodejs24` profile
admits only a coordinator-validated `ai-assisted-custom` tree for the same
reviewed Node.js 24/strict TypeScript family. Its request binds one Prompt 24D
extension ID, candidate bundle and source-tree digests, the complete Prompt 29A
deterministic scaffold and semantic-input digest, a separately derived Prompt
32A envelope, exact AI-owned paths, and no unresolved behavior.

Admission proves that every workload-scoped generated path and byte remains
unchanged, user-owned bytes remain preserved, and every AI-authored file maps to
one declared non-generated extension point. The derived envelope must enumerate
the complete final path/checksum set while preserving the exact handler,
runtime, toolchain, package/lock paths, dependency coordinates, offline cache,
required checks, and fixed shell-free command sequence. Candidate source cannot
select commands, install a new dependency, or broaden runtime authority.

A passing AI-assisted run must satisfy lint, type-check, unit and contract
tests, no high/critical dependency finding, no secret finding, compile,
deterministic package, and reproducibility. It returns level-5
application-build-and-tests Evidence and `ai-assisted-build-artifact` provenance
bound to the extension, candidate bundle, source tree, deterministic scaffold,
build request, lock, and Solution Revision. A missing test, unresolved behavior,
ownership/provenance mismatch, tool failure, or scan finding returns no package
and cannot claim `ai-assisted-custom-validated`.

The runner validates a candidate; it does not accept one, mutate source, write a
repository, alter canonical contracts or coverage, call a model, use cloud
credentials, upload, plan, apply, or deploy. The original deterministic
generated-source profile remains unchanged and preferred.

The aggregate image source archive preserves the generator’s exact paths,
including contract basenames over the 100-byte ustar field. Its only permitted
extended header is one POSIX per-file `path` record of at most 1024 bytes,
including the canonical decimal length and newline. The existing 512-byte
application path ceiling and complete source manifest still apply. The header
and immediately following regular file use the same SHA-256-derived placeholder.
No global, chained, duplicate, size, link, ownership, sparse or unknown metadata
is accepted. Historical plain ustar inputs remain readable; older images reject
the new path form and must not be selected for those inputs. This changes only
transport representation, preserving source identities and bytes.

The workspace per-file limit continues to apply to source and arbitrary
dependencies. Four exact files in the pinned offline toolchain exceed that
limit: the two TypeScript compiler modules and the Linux musl Rolldown and
Lightning CSS bindings. Admission requires their exact path, byte length and
SHA-256 before applying the exception. They still count toward total workspace
bytes/files, and every later step must preserve their bytes and mode. A known
path with different content or an oversized unlisted dependency fails closed.

Actual generated-code acceptance uses regular pnpm executable shims, with
`prefer-symlinked-executables=false`; all workspace links remain forbidden.
Vitest runs with `--no-cache` so it does not mutate the bound dependency tree.
The production-prune stage uses `install --prod` with the same exact offline
store, frozen lock/store, no-hook, no-runtime and layout options as admission.
Before the production install, the executor verifies the exact installed and
compiled trees, then removes only its owned `application/node_modules` tree. The
frozen production install starts clean: an incremental hoisted install otherwise
leaves development shims. The default prune command also changes layout and
tries network resolution.

Trivy’s pinned pnpm analyzer may emit a nonempty package inventory without an
empty findings property. Only its exact `pnpm-lock.yaml` / `lang-pkgs` / `pnpm`
row with valid package identities admits that omission. Malformed collections
remain errors. The package runner rejects oversized scan collections instead of
truncating them, so a finding after the previous 256-entry cutoff cannot produce
a passing artifact.

## Fixed-seed candidate host

The separate host-repair-seed package entry exposes distinct fixed-control and
bound-repair contracts. Candidate admission reconstructs the fixed 1.1.0 seed,
permits only its one user-owned extension to change, and preserves generated
files, dependencies, commands and isolation. Both paths share actual execution,
output inventory, ZIP reproducibility and cleanup checks; candidate artifacts
carry host-only ownership incompatible with normal export Evidence.

The API's private `createProductionSeedCandidateValidationHost` restores the
original seed receipt/request, binds its tenant and invocation to known usage,
materializes the actual response patch and owns the runner call. It obtains the
materializer through the declared existing workspace package instead of copying
patch or content-safety logic. No new external dependency is introduced.

The source-owning host still returns only unissued RAM observations. The private
authenticated sequence journal now calls that host itself, joins its exact
issued input and stored dispatch/usage, and writes a strict metadata receipt
plus V4 stage outcome through unregistered proposal 0068. Current authorization,
configuration and active canonical/runtime leases are checked before and after
the actual runner. No SQL transaction spans native execution.

Receipts bind the raw response digest, candidate source tree, patch lineage,
runner report and observed usage. The exact remaining TS2322 diagnostic permits
a repair; unrelated failures cannot claim that defect. Infrastructure errors or
unverified cleanup produce no receipt. Replay requires the identical response
and configuration; racing actual validations must agree on content and
disposition. Source-free recovery retains original-tenant checks and grants no
further action.

The private first-stage provider dispatcher now supplies its actual response to
this journal. Second-stage lineage and whole-case financial completion remain
unfinished. No public route, normal export path, model activation or native
proof is established by the local synthetic tests.

The current fixed-seed model path uses explicit response V2: one exact patch,
without a model-computed result hash. Host materialization computes SHA-256 from
the actual patched UTF-8 bytes. The raw response digest, patch digest and
resulting file digest stay separate; the same isolated runner validates the
result. The legacy response and its supplied-digest verification remain
unchanged.

The first-stage private sequence host now composes the actual SDK and counted
pricing path with the retained platform reservation and immutable dispatch
journal. Current commercial, tenant/operator, model/candidate-host and actual
runtime/workflow lease checks occur before counting and again at physical send.
Only the journal that recorded the dispatch can authorize that send. Known
response usage reaches durable observation before candidate validation; unknown
usage remains held. No SQL transaction spans provider or native execution. This
does not yet complete second-stage lineage, terminal settlement or normal AI
activation.
