# OWASP ASVS Level 2-oriented verification matrix

> Public distribution note: links to internal historical plans and operational
> records are omitted here; the retained text describes the original decision or
> design.

## Scope and claim boundary

This matrix uses the official
[OWASP Application Security Verification Standard 5.0.0](https://owasp.org/www-project-application-security-verification-standard/)
and version-qualified identifiers from the
[official ASVS 5.0.0 release tree](https://github.com/OWASP/ASVS/tree/v5.0.0_release/5.0).
Version qualification is intentional because requirement identifiers can change
between ASVS releases.

Cloud Markup targets an **ASVS Level 2-oriented engineering and verification
posture**. This is not an ASVS certification, attestation, audit opinion, or
claim that every Level 2 requirement is satisfied. The matrix is a controlled-
beta traceability baseline over requirements material to the current product.
Three explicitly labeled Level 3 requirements (`v5.0.0-5.3.3`, `v5.0.0-13.1.2`,
and `v5.0.0-13.1.3`) are included as selected defense-in-depth review
objectives; they do not raise or redefine the Level 2-oriented baseline.

Requirements not listed here are unassessed, not implicitly passed. A production
release must perform a complete applicability review against the pinned ASVS
release and retain independent manual/deployed evidence where required.

## Status vocabulary

| Status                | Meaning                                                                                                         |
| --------------------- | --------------------------------------------------------------------------------------------------------------- |
| `automated-evidence`  | Repository tests or static assertions exercise the stated bounded implementation.                               |
| `partial`             | Some automated or design evidence exists, but the full requirement or deployed operating control is not proven. |
| `manual-required`     | Deployment/configuration or human review evidence is required; repository tests cannot establish it.            |
| `blocked`             | A required production composition, policy, or control is deliberately unavailable.                              |
| `not-applicable-beta` | The feature is absent from the controlled-beta scope; the rationale must remain true.                           |

None of these statuses means ASVS certification. `automated-evidence` is scoped
to the exact command and boundary named in the row.

## Explicitly absent or not applicable beta surfaces

- GraphQL and WebSocket APIs are not exposed. Requirements specific only to
  those protocols are `not-applicable-beta`; adding either reopens this matrix.
- WebRTC is absent. ASVS chapter V17 is `not-applicable-beta`.
- Cloud Markup does not collect card data; Stripe-hosted surfaces own payment
  entry. Requirements for application storage or display of card details are not
  applicable to the current boundary, while redirect, webhook, identifier, and
  entitlement controls remain applicable.
- Customer Terraform state is not stored by Cloud Markup. State protection is a
  customer-owned CI/CD responsibility; Cloud Markup must still prevent state or
  plan sensitive values from entering exports, logs, or Evidence.

## Evidence maintenance

For a beta review, record the exact commit, command, test count/result, CDK
template digest, reviewer, date, environment, and manual artifact for every row
claimed beyond `blocked`. A newer security-relevant commit or configuration
invalidates earlier manual evidence until reviewed. Failures and skipped checks
remain visible. This matrix must be updated when an authentication path, data
class, external service, runtime, generated workflow, or deployment boundary
changes.
