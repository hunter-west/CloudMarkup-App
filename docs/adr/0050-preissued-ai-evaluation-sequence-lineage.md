## Context

The frozen full-beta evaluation includes repair success and repair exhaustion.
Both require genuine validation of the actual candidate after each model repair.
The current V2 plan, selected invocation set, journal and observation
authenticate one exact prepared input and one primary invocation per case. A
second repair's input does not exist until the first repair and deterministic
validation finish. Reusing its primary input digest or retrospectively choosing
a favorable run would misrepresent both authorization and quality.

[ADR-0035](0035-deterministic-ai-evaluation-and-runtime-admission.md) requires
frozen expectations, exact input evidence, current runtime/commercial controls
and genuine deterministic evidence.
[ADR-0043](0043-platform-model-dispatch-spending-fence.md) requires a separately
fenced real send for every attempt. These accepted requirements remain
unchanged. This proposal chooses a durable way to bind future input derivation
and all outcomes; it grants no inference or deployment permission and does not
accept the proposed memory-preview decisions by proxy.

## Decision

Introduce explicit V3 evaluation sequence contracts beside the unchanged V1/V2
paths. The first host-reviewed recipe admits only the existing frozen
repair-success and repair-exhaustion cases, using two ordered candidate.repair
slots with the repair-escalation role. Each slot's permitted route, model,
prompt, schema and catalog tuple is approved before any output exists. IDs for
all slots are generated once by the authenticated host during immutable
selection issuance. Idempotent issuance returns those stored IDs. An existing
invocation prevents retrospective sealing; failed runs cannot be replaced.

The plan approves a closed input recipe, predecessor identity and fixed budgets,
not an invented future payload digest. Before each eligible dispatch, the host
must derive the input from actual bounded RAM bytes and the exact prior
validation receipt, verify original ownership/revision bindings, and issue
immutable input metadata. It binds the complete prepared payload, prior output
and merged-candidate digests, sanitized diagnostics, recipe, stage and
invocation. Caller-supplied digests alone are not derivation evidence.
Repository-origin recipes must reference the separately issued pinned
parser-input authority.

The first slot requires a genuinely validated synthetic invalid seed. The second
is eligible only after slot one has a genuine repairable validation failure.
Success, exhaustion, nonrepairable failure, cancellation and unavailable RAM
have explicit outcomes. Every pre-issued slot ends in one accountable state,
including not-required, not-dispatched, known provider/validation failure and
unknown dispatch. Unknown usage remains held for canonical reconciliation; it is
never projected as zero cost, no dispatch or successful quality evidence. Finite
transition projection checks metadata; it is not a receipt issuer.

Authenticated adapters must recheck current operator approval, original tenant,
project and principal, time, configuration, entitlement and kill switches at
selection issuance, input issuance, admission, final guarded send and outcome
acceptance. Preserve the established organization-then-plan lock order. Bind all
real attempts to the canonical commercial workflow and accepted estimate; retain
per-call pricing, complete CountTokens input, conservative uncertain charges and
the USD 50 platform cap. Lineage readers and transitions perform no financial
writes or reconciliation.

Temporary prompts, responses, diagnostics and generated bytes remain in bounded
session RAM and deliberately disappear on restart. The separately reviewed RAM
runner must prove actual execution, produced-byte identity and cleanup before
pass. Metadata recovery may restore financial truth but cannot regenerate lost
content or resume a child invocation. All dispositions remain available to a
future report issuer; it cannot drop failed attempts or revise frozen criteria.
Normal admission still requires a separate immutable report, current promotion
and complete product wiring.

## Consequences

### Positive

- Future inputs can be authorized through an exact reviewed recipe without
  pretending their bytes already exist.
- Every attempted or unused stage remains attributable to one pre-result
  selection, preventing favorable-run substitution and understated usage.
- Existing V2 single-call receipts and recovery stay readable and unchanged.

### Negative

- Explicit V3 plan, input, terminal and canonical accounting bridges are needed;
  appending IDs to the V2 set is insufficient.
- Loss of RAM can make an evaluation incomplete even when financial recovery
  succeeds. Re-execution needs a new independently authorized run and cannot
  replace the original failed or unknown lineage.
- Real validation and native RAM execution remain prerequisites; deterministic
  synthetic provider tests cannot establish hosted model quality.

### Follow-up

- Implement strict provider-neutral schemas and finite transitions, then private
  authenticated issuance, stage receipts and the same-operation repair bridge.
- Keep prospective SQL 0058 outside runtime migration discovery until the actual
  0056 selection and 0057 parser-receipt chain is integrated and verified. Use
  additive immutable metadata tables; preserve historical SQL and explicit V2
  parsing. No new dependency or provider-specific domain import is required.
- Prove coherent substitutions, current-authority races, direct SQL bypasses,
  cancellation/unknown outcomes, exact budget accounting, source ownership,
  RAM-only process boundaries and cleanup. Run required workstream, security,
  compatibility and migration gates before integration.
- Before any activation, omit V3 host registration to disable this path. After
  issuance, retain immutable metadata and canonical recovery; roll forward and
  never delete or reassign stages to conceal a failed evaluation.

## Alternatives considered

### Keep one V2 invocation per case

This remains supported for existing single-call cases, but cannot authenticate
repair children whose exact input is derived from later results. It does not
satisfy the two existing frozen repair cases.

### Select successful attempts after execution

Rejected because it changes the evaluation sample, loses failed or unknown
attempts and permits understated costs. A later report is only a projection of
pre-issued complete lineage, not selection authority.

### Persist content to resume interrupted sequences

Not selected under the owner's RAM-only temporary-AI requirement. Reconsidering
this requires an explicit product/security decision with retention, encryption,
authorization and deletion semantics; it is not an implementation fallback.

### General workflow engine for arbitrary operation graphs

Deferred. The first two ordered same-operation slots cover the concrete repair
need. Mixed-operation architecture, generation and import sequences require
separately reviewed recipes, prompt/accounting authority and genuine validators.

## Proposed host execution implementation appendix

The fixed host runner uses a distinct host artifact-manifest discriminator and
JSON artifact. It reuses only the normal runtime leaf schema and deterministic
ZIP primitive, without acquiring normal artifact or Evidence authority.

Both policy factories independently validate their own unchanged profile, then
project only the exact container tuple into a private isolation configuration.
The new host factory is exported only from the host subpath. A transient
optional open.signal reaches initialization and all helper operations; cleanup
retains its bounded per-control grace independent of abort. One execution
deadline spans both independently initialized positive sessions, their nine
commands, cleanup and packaging. Overdue cleanup cannot produce success even
though cleanup continues safely beyond that execution deadline.

No AI sequence stage, current operator/tenant authority, financial reservation,
report issuer or promotion is added by this proposed execution adapter.

## Proposed first host-seed request contract

The first repair source has fixed-host-synthetic provenance and user-owned file
semantics. V1 candidate.repair input requires ai-authored-candidate ownership,
so it cannot honestly describe that source. Add a distinct V2 host-seed request
with one exact file, the existing candidate-artifacts-only boundary,
first-attempt identity, two-attempt ceiling, sanitized observed diagnostics and
references to the seed receipt, source tree, ownership, revision and recipe.
Preserve V1 request and response bytes. New model outputs still use the existing
V1 unaccepted AI-candidate response and exact prior-file digest; they never
become user-owned merely by generating them.

Host preparation reconstructs the fixed source only after RAM admission and
compares every current host/source binding with the seed receipt. A private
authenticated adapter reads the issued record before preparation and verifies
original/current operator authority, tenant membership, configuration, receipt
and cancellation again afterwards. Preparation emits no durable stage receipt or
model authority. The existing V1 gateway still rejects this V2 input.

The next composed V3 stage issuer must bind the complete prepared V2 payload to
the pre-issued first slot and exact seed receipt. Current authority and complete
CountTokens/commercial fences remain necessary at dispatch. A parser extension
or cast cannot substitute for that issuer. Later model-output repair continues
to preserve actual AI provenance. Do not silently reinterpret the frozen V1
repair prompt, recipe or historical approvals.

Alternatives are to relabel the host file as model output, silently broaden V1,
or run an extra unapproved generation call to manufacture a predecessor. Each
would lose exact provenance or alter approved lineage. A separate input version
costs an explicit transport/authority integration but leaves prior behavior
readable and rollback available by omitting the new host. This appendix remains
Proposed alongside ADR-0050; it grants no inference or activation authority.

The separate host-seed V2 transport projection now preserves the explicit input
contract. Its CountTokens entry counts the full system, messages, response
schema, cache and thinking input under the existing request-local authorization,
expiry, cancellation and single-send checks. Existing V1 projection output and
count policy meaning are unchanged. This is pure projection and guarded counting
only: V3 durable input issuance, real per-attempt accounting, provider dispatch
and current host registration remain required. No inference call is introduced.

## Proposed dispatch and observed-attempt ordering

Keep the V3 prototype contracts and artifacts unchanged. Add V4 dispatch,
observed-attempt and stage-outcome records that explicitly reference the V3
plan/selection/input. Dispatch binds the accepted canonical workflow
fingerprint, recorded dispatch intent, exact planned call and stage ordinal
before HTTP. Only after actual usage exists can the host issue an observed
canonical attempt. Known stage outcomes reference that observation. They do not
require or invent the whole-workflow terminal before the repair successor can
run.

Both pre-issued stages share one accepted canonical workflow and budget; each
physical send has its own platform spending reservation. Stage and canonical
attempt ordinals are one/two, while the provider attempt for each bounded send
is one. No retry/escalation or extra reservation is inferred. The final case
joins actual canonical settlement only after its stages end. Unknown or lost
execution stays held until authentic recovery establishes financial truth.

The shared finite projection checks exact metadata joins and returns
lineageComplete separately from accounting. It authenticates no row or usage and
cannot activate a model. Durable issuance still belongs to the current
tenant/operator-authorized host transactions. Omitting the successor host keeps
it disabled; existing V1/V2/V3 readers and serialized artifacts remain intact.
This is an implementation refinement of the proposed sequence design, not a
change to accepted ADRs or permission to infer missing receipts.

## Proposed host-computed patch response

The fixed-seed input has user-owned semantics and therefore admits only an exact
patch. Its initial prompt requested a whole-file response, and the V1 patch
shape also requires the model to calculate a SHA-256 of newly proposed bytes.
Neither requirement is a reliable boundary for the live host.

Add a separate host-only response V2 and prompt version 1.1.0. The model
supplies one exact patch and copies the existing base/provenance references. It
declares host digest computation and cannot include proposedResultDigest. The
pure host applies the patch to the exact source, computes the resulting file
digest and then runs the unchanged candidate validator. Raw response, patch,
source and validation identities remain distinct. Shared grounding, channel and
ownership checks preserve the previous rejection behavior.

The original prompt and V1 response retain their exact bytes and mandatory
model-supplied hash verification. Current authenticated preparation selects the
new prompt/tool; its frozen authority tuple, complete token count and spending
quote bind that exact response schema. Existing metadata stays readable through
its explicit version. The new tool remains outside the normal V1 registry.

Ignoring the old required hash would silently weaken V1; inserting a host hash
into a claimed model response would misstate provenance. A separate protocol
costs one schema and version-aware dispatch integration, but makes the digest a
deterministic host result without granting source, execution or tenant
authority. No migration or normal AI activation follows from this protocol
change. Existing candidate metadata binds the actual response digest and issued
invocation; rollback omits the new current host configuration. Genuine
evaluation and final native/release gates remain prerequisites. This refinement
remains Proposed and does not alter accepted ADRs.
