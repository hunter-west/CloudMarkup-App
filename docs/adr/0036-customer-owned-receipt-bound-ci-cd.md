# ADR-0036: Customer-owned receipt-bound CI/CD

> Public distribution note: links to internal historical plans and operational
> records are omitted here; the retained text describes the original decision or
> design.

- **Status:** Accepted
- **Date:** 2026-08-24
- **Owners:** Cloud Markup engineering
- **Supersedes:** None
- **Superseded by:** None

## Context

Cloud Markup can export an immutable, reviewed Solution package to a customer
repository, but it cannot operate customer cloud accounts under ADR-0005.
Customers still need repeatable validation, planning, deployment, smoke, and
drift workflows. Those workflows cross several trust boundaries: repository
content is mutable, GitHub pull requests may be untrusted, Terraform plans may
contain sensitive values, cloud credentials can change infrastructure, and a
later job can accidentally consume a different commit, revision, backend,
workspace, lock, or plan.

The product therefore needs a durable boundary between generating workflow files
as reviewable data and exercising deployment authority. The boundary must also
preserve the existing GitHub App rule that workflow-file writes require both
explicit user confirmation and an already-approved App permission.

## Decision

Cloud Markup deterministically generates and validates one versioned,
allow-listed customer workflow set for no-credential verification, planning,
exact saved-plan deployment, bounded smoke checks, and read-only drift
inspection.

The workflow files are generated Solution-package inputs. They are never
executed by Cloud Markup. The customer owns the repository, GitHub Environments,
OIDC provider and trust policies, environment-scoped role variables, Terraform
state and locks, approvals, artifact access and retention, workflow execution,
incident response, and every cloud change.

Credentialed jobs use short-lived GitHub OIDC sessions and distinct
customer-owned roles for plan, deploy, and read-only drift. The bounded HTTPS
smoke workflow has no OIDC or cloud role. Trust is scoped to the exact private
repository and GitHub Environment using reviewed immutable repository and owner
IDs, exact names, an exact Environment-qualified subject, and `StringEquals`,
while workflow admission separately checks approved branch references.
Pull-request validation is credentialless and performs inert package checks
without invoking Terraform or provider code. It cannot use an untrusted
pull-request trigger that receives privileged credentials. Ephemeral deployment
is schema-disabled by the v1 configuration until a separately reviewed
isolated-target, budget, cleanup, and authenticated-test contract exists.

Planning first verifies the exact immutable Solution package, then creates a
Terraform saved plan. Its manifest binds the plan checksum, sanitized analysis,
Terraform version, provider lock, Solution Revision, commit, environment,
backend, workspace, package manifest and lock, infrastructure inputs, workflow
configuration, policy, exact target account and Region, digests of all three
role ARNs, exact OIDC subject, encryption metadata, and expiry. The saved plan
is encrypted before upload with an ephemeral AES-256-GCM key wrapped by the
reviewed RSA public key using RSA-OAEP-SHA256; RSA keys shorter than 3072 bits
are rejected. The environment-scoped private key is not generated or exported.
Deployment cannot re-plan. It decrypts only to runner-temporary storage and
applies only that exact manifest-bound plan after customer environment approval
and integrity checks pass.

Deployment emits a receipt, not canonical Evidence. Smoke and drift jobs obtain
and verify that receipt, check out its exact commit and target authority, and
emit successor receipts and stage-specific Evidence. Only passing smoke is
deployment Evidence; drift Evidence is an observation of drift inspection. Raw
plan JSON, the plaintext saved plan, and raw drift plans are removed before
artifact upload. A receipt or Evidence record is an observation, not design or
deployment authority.

Workflow generation uses a closed full-commit action registry and fixed paths.
The exact `hashicorp/aws` provider source, provider lock source/version/hashes,
Linux AMD64 Terraform CLI checksum, and Terraform package-tree digest are closed
inputs. Modules and provisioners are rejected, and module fetching is disabled.
Any changed generated byte, unsafe trigger, unreviewed secret reference,
credential shape, unpinned action, planning apply, deployment re-plan, or drift
apply is rejected. Writing workflow files still requires an exact file preview,
explicit user confirmation, and existing GitHub App Workflows permission. Cloud
Markup never requests a permission expansion automatically.

This decision refines ADR-0005 without superseding it: generated customer
automation is an export artifact, not a Cloud Markup deployment capability.

## Consequences

### Positive

- Every privileged stage is customer-owned, environment-scoped, auditable, and
  bound to the exact predecessor artifact.
- Plan substitution, cross-environment plan reuse, stale plans, and silent
  deployment re-planning fail closed.
- Untrusted pull requests can run only the credentialless verification path.
- Sanitized Evidence can describe plan, smoke, and drift observations without
  making them canonical design state. Deployment itself produces only a receipt.
- Generated files remain deterministic and can be previewed, compared, and
  confirmed through the existing GitHub export flow.

### Negative

- Customers must configure and maintain multiple IAM roles, GitHub Environments,
  Terraform backends, artifact retention, and incident procedures.
- A generic rollback cannot be promised; recovery remains specific to the
  customer application and infrastructure.
- Artifact retention and GitHub run access become operational dependencies for
  receipt-bound smoke and drift jobs.
- The credentialless validation workflow cannot be called production-ready until
  customers have a reviewed distribution of the Prompt 33B CLI pipeline.
- Configuration cannot prove the selected GitHub Environment protection rules;
  activation also requires an authoritative execution-boundary verification of
  reviewers and allowed deployment branches.

### Follow-up

- Publish and review an operational Prompt 33B CLI distribution before beta
  activation of the credentialed planning path. The generated plan workflow
  currently enforces this as a hard credentialless preflight hold before OIDC.
- Add authoritative GitHub Environment-policy verification before beta
  activation. Previewed names and customer setup instructions are not
  authoritative evidence of required reviewers or branch restrictions.
- Design and review a target-specific ephemeral-test contract before changing
  the current schema-level denial.
- Keep action pins, Terraform versions, provider locks, trust-policy examples,
  and sanitization behavior under security review.
- Prompt 47B may consume drift artifacts as observations while preserving their
  revision, environment, staleness, and evidence authority.

## Alternatives considered

### Cloud Markup-operated deployment

Rejected because it would require customer credentials, state, approvals,
rollback, drift, and incident ownership and would conflict with ADR-0005.

### Long-lived GitHub or AWS keys

Rejected because repository secrets expand persistence and exfiltration risk.
Short-lived, environment-scoped OIDC sessions provide a smaller trust boundary.

### Re-plan during deployment

Rejected because approval would no longer refer to the bytes that are applied.
Any stale or mismatched plan must be regenerated and approved.

### One role for every stage

Rejected because plan, deployment, and drift have materially different
permissions and blast radii. Separate roles make least privilege reviewable; the
bounded smoke probe intentionally receives no cloud role.

### Upload raw plan output

Rejected because Terraform plan data may contain sensitive values. Only the
RSA-OAEP-SHA256/AES-256-GCM encrypted envelope may be uploaded; the deploy job
decrypts to temporary storage and removes the plaintext. Summaries and Evidence
use bounded sanitized projections with hashed resource identities.
