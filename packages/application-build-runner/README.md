# Application build runner

> Public distribution note: links to internal historical plans and operational
> records are omitted here; the retained text describes the original decision or
> design.

`@cloudmarkup/application-build-runner` is the provider-neutral boundary for the
exact Node.js 24/TypeScript workload family. It admits either immutable
deterministic generated source or an explicitly bounded AI-assisted custom
candidate, resolves only an integrity-bound approved offline lock, runs a fixed
lint/type/test/scan/compile matrix through an injected isolated executor, and
returns deterministic Lambda artifacts, SBOM data, diagnostics, coverage
assessment, and Evidence v1.

It does not mutate source or lockfiles, run package scripts, accept arbitrary
commands, use credentials or public networks, call AWS, inspect Terraform,
upload artifacts, accept candidates, write repositories, or deploy.
User-provided source is rejected by the executable profiles and remains
static-only under the explicit safe profile.

## Profiles and execution

The generated profile accepts only conflict-free `generated-starter` or
`complete-supported-pattern` source and one exact generator build envelope. It
requires a pnpm v9 frozen lock with integrity/tarball digests, an approved
prepackaged store, disabled lifecycle scripts, and the exact Node.js 24/
TypeScript 6 toolchain. The fixed shell-free sequence is install, lint,
type-check, generated unit tests, generated contract tests, offline dependency
and secret scans, compile, then an explicit production-only dependency prune.
Both scanner invocations use the frozen database with offline scan enabled and
database updates, telemetry, and version checks disabled by the command
allowlist. The approved install uses the hoisted copy linker with package bins
and symlinks disabled; package-manager workspace/configuration hooks are ignored
by the command and forbidden in source.

The additive `cloudmarkup.application-build.ai-assisted-custom-nodejs24` profile
reuses that same runtime, dependency allowlist, offline store, limits, and
nine-command matrix. Its `ai-assisted-custom` source input must bind:

- an exact AI-authored extension ID present on the Solution Revision;
- the complete deterministic AI scaffold and its semantic revision input digest;
- a separately derived `ai-assisted-custom` application-build envelope;
- the final source-tree digest and candidate-bundle digest;
- the exact AI-owned paths; and
- an empty unresolved-behavior list.

The runner verifies that every workload-scoped scaffold path remains present,
all generated bytes and labels remain exact, user-owned bytes remain preserved,
and only a non-generated path carrying deterministic extension-point provenance
and declared by the workload contract may become `ai-authored`. The external
envelope must bind the complete final path/checksum inventory, exact fixed
package/lock-contract/manifest paths, full required-check set, initial runtime,
toolchain, and dependency coordinates. Missing unit or contract tests, path or
ownership overlap, profile mismatch, unresolved behavior, or any source,
candidate, scaffold, revision, envelope, lock, or content digest mismatch blocks
execution. This profile does not regenerate deterministic files or broaden the
dependency allowlist.

The explicit user-source safe profile performs static lint/type/scan checks
only. It does not install or select offline-store packages, execute user code,
package an artifact, or confirm complete coverage. Imports that the fixed static
toolchain cannot resolve fail closed; this profile does not synthesize an
executable repository-dependency view.

`createLocalApplicationBuildContainerExecutor` uses a digest-pinned Docker or
Podman image with network denied, read-only root, non-root UID, no capabilities,
no-new-privileges, a single disposable workspace, and hard CPU/memory/PID/time/
file/output bounds. The configured image and offline store are not built or
published by this package. After validating an exact fixed invocation, this
per-step adapter selects only the corresponding absolute
`/opt/cloudmarkup/bin/{pnpm,eslint,tsc,vitest,trivy}` wrapper through the
container runtime's `--entrypoint` option; only that invocation's already-
approved argument array follows the digest-pinned image reference.

At workspace admission the adapter seals a canonical path, directory mode, file
mode, size, and SHA-256 authority for every source, test, configuration,
package, and lock entry. Lint, type-check, both tests, and both scans receive a
read-only workspace mount. Install may add only `application/node_modules/**`,
compile may add only `application/dist/**`, and production prune may change only
node_modules; the adapter verifies exact source authority and the accepted
dependency/compiled snapshots at every transition and again before collection.
Unexpected paths, deletions, replacements, portable collisions, links, unsafe
modes, test-driven dependency changes, and post-compile mutations fail closed.
Only the two Trivy steps receive a second writable mount: a private temporary
cache bound at `/tmp/cloudmarkup-trivy-cache`. The image wrapper admits only
regular, single-link, byte-identical copies of its frozen database and metadata;
all other steps receive no scanner-cache mount. Session disposal removes both
the application workspace and this cache. The cache never enters source,
artifact, or evidence authority.

Passing generated or AI-assisted runs return a deterministic store-only Lambda
ZIP, CycloneDX SBOM, exact checksums/provenance, level-5 application build/test
and security Evidence, and a coverage confirmation. AI artifacts retain the
`ai-assisted-build-artifact` label and bind the extension ID, candidate bundle,
source tree, deterministic scaffold, build envelope, lock, revision, and build
request. Packaging includes generated runtime files and, only for the AI
profile, exact `ai-authored` runtime files; user-owned files remain excluded.
Evidence and artifacts are exposed as passing only after install, lint,
type-check, unit tests, contract tests, both scans, compile, production prune,
package, and reproducibility all pass.

On POSIX hosts the adapter maps the container to the invoking unprivileged host
UID/GID, so its private `0600` source files and disposable workspace are usable
without root ownership. Hosts running as root fail closed. Windows keeps the
fixed unprivileged container identity and host ACL boundary.

After production pruning, collection rejects every symlink/device, residual
development package, `.pnpm`/`.bin` tree, unknown hidden entry, and package
identity outside the exact runtime/transitive-runtime lock inventory. Only
regular runtime bytes are offered to deterministic ZIP assembly. Any admission,
command, test, scan, cleanup, package, or reproducibility failure returns no
deployable artifact and downgrades coverage.

The request and result bind the exact environment, Solution Revision ID/digest,
generation or scaffold artifact digest, canonical build-request digest, build
contract, toolchain, dependency lock, and source checksums. Passing generated
coverage preserves its starter/complete state; passing AI coverage is labeled
`ai-assisted-custom-validated`. Every failure downgrades to custom
implementation required. Public result parsing independently verifies artifact
bytes/checksums, source provenance, Evidence commitments, and the canonical
report digest.

## Orchestration handoff

The local adapter regression injects only a test-scoped process boundary while
exercising the real workspace/session and runner. It asserts exact Docker argv,
regular production-only dependency collection, deterministic ZIP bytes, and
fail-closed link/prune cases plus source, dependency, unauthorized-path,
hard-link, and compiled-output mutations without starting Docker or using a
network.

The Solution export workflow calls an injected application-build port only for a
conflict-free generated-starter or complete-supported-pattern result with an
exact application-build envelope. That existing generated-source path is
unchanged. The AI-assisted candidate profile is a separate candidate-validation
entry point: a coordinator may invoke it only after producing the strict
extension/scaffold/envelope bindings above. The runner never accepts the
candidate on the user's behalf or materializes it into a repository.

User-provided, external, and infrastructure-only workloads cannot enter an
executable profile.

The workflow persists the exact build report and Evidence before interpreting
success. A failed lint, type, unit, contract, dependency, secret, package, or
integrity check blocks export publication and retains the runner's explicit
coverage confirmation/downgrade without mutating the immutable Solution
Revision.

## Opt-in memory-only executor

The separate `createMemoryApplicationBuildContainerExecutor` uses a
digest-pinned successor helper image and verified tmpfs workspaces. The
historical local executor is unchanged and does not claim memory-only handling.

Call `assertMemoryApplicationBuildHost()` before receiving candidate bytes,
including before model dispatch or consuming a source stream. The executor
rechecks host admission before each container operation. This is a current
environment check, not a durable authorization or evaluation receipt.

Admission requires native Linux, the same kernel identity as Docker, no active
swap, disabled current-process core dumps, no automatic heap snapshots, and
actual tmpfs mounts supporting `noswap`. Docker Desktop/WSL and remote kernels
are rejected. No host settings are changed. The caller must also exclude
privileged external snapshots, hibernation and crash capture from its trusted
execution environment.

The helper receives bounded data through stdin and returns bounded metadata or
regular-file bytes through stdout. It has fixed probe/seed/inspect/prune/collect
verbs; no source-controlled executable or shell is accepted. Workspace and cache
volumes must be exact owned tmpfs mounts. Each container also receives a fresh
private local-driver tmpfs volume for /tmp, with verified noswap/noexec and
mode0700. This avoids Docker's incompatible --tmpfs option parser while
preserving kernel safeguards. Temporary volumes are removed and absence is
verified after each container; they are never reused between steps. Tool
containers enforce disabled logging, network isolation, read-only root, non-root
execution and resource/core limits; read-only step mounts and the existing
file/dependency guards remain.

A failed operation closes the session to further execution or collection.
Successful completion requires exact verified cleanup. Public request, result,
package and Evidence v1 schemas retain their meanings.

The successor image and real Linux execution proof are still unverified in this
source checkpoint. See the execution plan and proposed
[ADR-0049](../../docs/adr/0049-memory-only-candidate-build-execution.md).

The memory executor admits a page-aligned scanner cache up to 1.5 GiB. The
frozen September 10 vulnerability database alone occupies 1,382,703,104 bytes;
the native proof uses that ceiling to retain database metadata and bounded
scanner writes. This private cache remains tmpfs with noswap and is removed with
the exact owned session. It does not expand the container memory limit.

## Fixed host repair seed contracts

The additive `@cloudmarkup/application-build-runner/host-repair-seed` export
provides strict in-memory source/request/result schemas and pure byte admission
for one fixed host-authored TypeScript control. It is separate from the normal
runner and artifact exports. Trusted composition must supply the actual reviewed
source factory output, approved lock/policy/helper pins and environment. The
admission regenerates the original scaffold, preserves every original generated
byte and allows only the fixed declared control suffix.

The returned inventory is host-only metadata; parsing a consistent tool result
is not proof that a tool ran and cannot issue AI, commercial or deployment
authority. No public host repair route is wired. Actual Go normalization parity
and complete RAM-only positive/invalid native controls are required before
evaluated execution. The new schema artifact is exported through
`./schema/host-repair-seed-v1`; its generator supports a strict `--check` mode.

## Fixed host control execution

The separate host entry now exposes `createApplicationHostRepairSeedRunner` and
`createMemoryHostRepairSeedContainerExecutor`. The runner admits only the fixed
trusted recipe, classifies the exact intended TS2322 observation and requires
two independent nine-command positive sessions, identical ZIP bytes and verified
cleanup before passing. Its manifest and artifacts remain host-only. No normal
API, model dispatch, evaluation receipt or report path is connected. The local
source checkpoint passed synthetic orchestration and compatibility tests; actual
native controls and full manifest normalization parity remain required.

Recipe 1.1.0 corrects the fixed seed entity identifier and uses a numeric
expression that satisfies the unchanged lint policy. Recipe 1.0.0 retains its
exact suffix semantics; current production source restoration selects only
1.1.0. Both versions remain unvalidated source until the actual native tools
run. The sole additive schema option preserves historical request shapes.

## Bound repairs of the fixed host seed

The host-repair-seed subpath also exposes the explicitly separate
`createApplicationHostRepairCandidateRunner` and
`createMemoryHostRepairCandidateContainerExecutor`. The candidate profile admits
one repaired extension against the reconstructed 1.1.0 invalid seed. Its request
binds base-file, invocation, input, patch and response digests; trusted host
composition must obtain these from the actual provider response. Pure parsing
does not establish provider execution or tenant authority.

Generated source, dependencies and tool/isolation configuration stay exact.
Candidate and control runs share the fixed command, packaging, reproducibility
and cleanup algorithms. Candidate artifacts have distinct host-only ownership;
they cannot enter normal exports or historical fixed-seed contracts. The
[checked candidate schema](json-schema/application-host-repair-candidate-v1.schema.json)
is verified by the existing host schema generator.

Synthetic tests cover admission, two executions, failed checks, changed ZIPs,
cleanup and native-memory denials. This checkpoint does not claim current native
tool proof, a production validator receipt or enabled AI.

## Final repair of the actual first candidate

The same host-only subpath exposes `createApplicationHostRepairSuccessorRunner`.
Its explicit V2 request and result bind the exact first candidate request,
report and lineage. Admission reconstructs that V1 predecessor and requires its
single repairable TS2322 observation with verified cleanup. Only its bound
extension can change. Both stages use the same one-file and result-bound checks,
command matrix, isolated executor and reproduction algorithm.

The final manifest records V2 origin while retaining host-only artifact
ownership. Historical readers reject it. The separate
[checked successor schema](json-schema/application-host-repair-successor-v2.schema.json)
is verified by the existing generator. The private journal must supply actual
RAM provenance and current authority; these structural readers cannot issue
receipts or authorize billing, export, another model call or a third attempt.
Synthetic orchestration is covered; actual final native evidence and the
complete authenticated sequence remain required before AI activation.
